Multi-Cloud GitOps Kubernetes Platform on AKS & EKS

Work · Production

A production Kubernetes platform spanning four clusters across Azure (AKS) and AWS (EKS) and hosting dozens of applications. It combines GitOps deployments, automated TLS and DNS, Gateway API ingress, and an on-demand preview environment for every pull request.

Pull request→ GitHub Actions build + Trivy scan→ ArgoCD ApplicationSet→ Preview env per PR
Merge to main→ ArgoCD GitOps sync→ AKS + EKS clusters production
ExternalDNS DNS records cert-manager TLS certs NGINX Gateway Fabric Gateway API→ Services
  • Infrastructure as code: the clusters and their node pools, including the GPU pools, are provisioned with Terraform, so the platform itself is reviewed and reproducible like any other code.
  • GitOps with ArgoCD: Git is the source of truth, so every deployment is reviewed, auditable, and easy to roll back.
  • Preview environments: GitHub Actions and ArgoCD ApplicationSets deploy an isolated environment for each pull request, so changes are tested before they merge.
  • Security in the pipeline: Trivy scans run in CI, so vulnerabilities are caught before they reach a cluster.
  • Self-service TLS and DNS: cert-manager and ExternalDNS issue certificates and create records automatically, so a new service gets an HTTPS hostname without a ticket.
  • Gateway API ingress: NGINX Gateway Fabric gives teams standard, role-oriented routing.
  • GPU workloads for AI: autoscaling GPU node pools serve the AI team. Taints and tolerations keep GPU nodes reserved for GPU workloads, so expensive capacity isn't spent on ordinary pods.
  • Progressive delivery (in progress): adopting Argo Rollouts so releases roll out gradually instead of all at once.
  • Result: 4 production clusters serving dozens of applications, all deployed through Git.

Client SSO Onboarding

30+ clients

A repeatable way to connect each client's identity provider to our platform. A Terraform module adds the client's IdP to AWS Cognito, and the client then confirms the connection works with SSO Checker, which runs on AKS. More than 30 clients have been onboarded this way instead of through manual console setup.

Terraform module per client→ AWS Cognito client IdP added→ SSO Checker SAML 2.0 sign-in test→ Pass / fail
  • Module, not console: every client is configured the same way, reviewed in a pull request, and easy to reproduce.
  • Self-service verification: clients test their own SSO connection and get a clear pass or fail, so there is less back-and-forth with support.

This site: Self-hosted on a Raspberry Pi, with a serverless backend on AWS

Source

A containerized Flask app runs on a Raspberry Pi and is exposed to the internet through a Cloudflare Tunnel. The visitor counter is serverless on AWS (API Gateway, Lambda, DynamoDB) and provisioned with Terraform, with remote state in S3.

Browser→ Cloudflare DNS + TLS→ Cloudflare Tunnel outbound only→ Raspberry Pi Flask container
Browser→ API Gateway→ Lambda Python→ DynamoDB
git push→ GitHub Actions→ Docker Hub amd64 / arm64→ Self-hosted runner on the Pi deploy + health check
  • Cloudflare Tunnel: the Pi opens no inbound ports on the home network. The tunnel is an outbound-only connection, and TLS terminates at Cloudflare's edge.
  • Multi-arch images: GitHub Actions builds for both arm64 and amd64, so the same image runs on the Pi and on cloud hosts.
  • Hybrid by design: the web tier costs almost nothing to self-host, and the counter API on Lambda costs pennies and is decoupled from the web tier.
  • Cost-driven migration: the site originally ran on ECS Fargate behind an ALB, which cost about $50 a month for a single small container. Moving it to a Pi cut hosting to near zero. The Fargate Terraform is still in the repo.
  • Automated deploys with rollback: a self-hosted GitHub Actions runner on the Pi deploys each commit's image, checks /healthz, and rolls back to the previous version if the check fails.
  • Runner security: the repo is public, so only pushes to main can reach the Pi's runner. Builds run on GitHub-hosted runners, and fork pull requests need approval.
