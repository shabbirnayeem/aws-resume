Multi-Cloud GitOps Kubernetes Platform on AKS & EKS

Work · Production

A production Kubernetes platform spanning four clusters across Azure (AKS) and AWS (EKS) and hosting dozens of applications. It combines GitOps deployments, automated TLS and DNS, Gateway API ingress, and an on-demand preview environment for every pull request.

Read moreShow less
Pull request→ GitHub Actions build + Trivy scan→ ArgoCD ApplicationSet→ Preview env per PR
Merge to main→ ArgoCD GitOps sync→ AKS + EKS clusters production
ExternalDNS DNS records cert-manager TLS certs NGINX Gateway Fabric Gateway API→ Services
  • Infrastructure as code: the clusters and their node pools, including the GPU pools, are provisioned with Terraform, so the platform itself is reviewed and reproducible like any other code.
  • GitOps with ArgoCD: Git is the source of truth, so every deployment is reviewed, auditable, and easy to roll back.
  • Preview environments: GitHub Actions and ArgoCD ApplicationSets deploy an isolated environment for each pull request, so changes are tested before they merge.
  • Security in the pipeline: Trivy scans run in CI, so vulnerabilities are caught before they reach a cluster.
  • Self-service TLS and DNS: cert-manager and ExternalDNS issue certificates and create records automatically, so a new service gets an HTTPS hostname without a ticket.
  • Gateway API ingress: NGINX Gateway Fabric gives teams standard, role-oriented routing.
  • GPU workloads for AI: autoscaling GPU node pools serve the AI team. Taints and tolerations keep GPU nodes reserved for GPU workloads, so expensive capacity isn't spent on ordinary pods.
  • Progressive delivery (in progress): adopting Argo Rollouts so releases roll out gradually instead of all at once.
  • Result: 4 production clusters serving dozens of applications, all deployed through Git.

A Terraform module adds the client's IdP to AWS Cognito, and the client then confirms the connection works with SSO Checker, which runs on AKS. This site: Kubernetes on a Raspberry Pi, with a serverless backend on AWS

Source

A containerized Flask app runs on a single-node k3s cluster on a Raspberry Pi and is exposed to the internet through a Cloudflare Tunnel. CI runs on ephemeral GitHub Actions runners inside the same cluster, and deploys are handled separately by Flux GitOps. The visitor counter is serverless on AWS (API Gateway, Lambda, DynamoDB) and provisioned with Terraform, with remote state in S3.

Read moreShow less
Browser→ Cloudflare DNS + TLS→ cloudflared pod outbound-only tunnel→ k3s on Raspberry Pi Flask Deployment
Browser→ API Gateway→ Lambda Python→ DynamoDB
git push→ GitHub Actions test + build→ Docker Hub amd64 / arm64→ Flux image automation→ Rolling update GitOps, separate homelab repo
  • No inbound ports: cloudflared runs as a pod and reaches the site by its Kubernetes Service name. The tunnel is an outbound-only connection, and TLS terminates at Cloudflare's edge.
  • GitOps deploys, zero cluster credentials in CI: CI only builds and pushes an image. Flux, running from a separate homelab repo, notices the new tag, commits it to Git, and reconciles the cluster — the pipeline that builds the image never touches Kubernetes directly (see Ephemeral GitHub Actions Runners below for how CI itself runs).
  • Zero-downtime rollouts: readiness probes on /healthz keep traffic on the old pod until the new one is healthy.
  • Multi-arch images: GitHub Actions builds for both arm64 and amd64, so the same image runs on the Pi and on cloud hosts.
  • Cost-driven migration: the site originally ran on ECS Fargate behind an ALB, which cost about $50 a month for a single small container. Moving the web tier to a Pi cut hosting to near zero, and the counter API on Lambda costs pennies. The Fargate Terraform is still in the repo.

Ephemeral GitHub Actions Runners on Kubernetes

Source

Self-hosted CI runners on k3s with Actions Runner Controller, mirroring a similar setup at work. Each job gets a fresh pod that is deleted when the job ends, and the pool scales to zero when idle. Runners authenticate with a GitHub App (short-lived tokens, no personal access token) and hold no Kubernetes credentials at all — they only build and push images, and deploys happen separately through Flux.

Read moreShow less
  • Flux-managed, not manual Helm: the controller and the runner scale set are each a Flux HelmRelease referencing the chart directly over OCI. releaseName matches the original manual helm install, so Flux adopted the running release in place instead of creating a duplicate.
  • No cluster credentials to leak: since runners never touch Kubernetes, there's no RBAC, ServiceAccount or kubeconfig inside a runner pod for a compromised job to abuse.
